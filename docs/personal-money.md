# Personal money (SPR-180)

Owner-only `/personal/money` on Admin (local/preview `/admin/personal/money`). Personal directory links here. Phone-first manual entry: expenses, gross income, refunds, opening funds, and transfers/exchanges with explicit received amounts. SGD, MYR and USD remain independent; no inferred exchange rates or combined totals. Integer minor units throughout. CSV exports the selected month's complete paginated ledger, including voids, in minor units and with spreadsheet formula protection.

Six jars use the owner’s configured monthly allocation after the tax provision. Amounts and account assignments are private database configuration, never public bundle constants. Planned banks are labelled as planned, not confirmed open. The LTSS target is configuration; no estimated reserve balance is posted. Enter verified opening funds manually. Recorded jar funds are entered movements through the selected month, not verified bank balances. No bank credentials or account numbers are required. Payment method is a bounded free-text label for Malaysian accounts/cash/cards too.

Recurring records store original currency, account, jar, purpose, category, cadence, due date, decision and notes. A server-only SQL invoker function locks the rule, records one payment and advances its next date atomically. Same-request retries return the existing record; a second request for the same occurrence is refused. Monthly/yearly dates retain the original billing day after short months/leap years. Overdue rules advance one occurrence at a time, not silently past unpaid bills. To change a rule, pause and add its replacement. Pausing tracking does not cancel a merchant subscription. No automated charging, bank connection, reminder schedule or push notification is implied.

Entries can be voided/restored, with original details retained. Corrections use void + replacement. Voiding a recurring payment does not rewind its due date; restoring it restores its spending contribution. Entry IDs enforce retry idempotency; changed content under the same ID conflicts. Income and opening funds are distinct; transfers never count as expenses. Business operating costs have a separate jar/scope; raw business revenue is not passive profit or disposable cash.

Security: stable owner + stored privileged role checked independently in the page and API. Canonical Admin host in production; local/preview only outside production. POST requires same-origin bounded JSON and strict Zod data. DB owner keys are derived server-side, never accepted from clients. New tables have RLS enabled with no browser policies/grants; invoker RPC execute is service-only. Every query is owner-filtered. No private cache, offline queue, secrets or model calls. Existing PWA service worker remains network-only. Monthly totals aggregate in SQL, lists use 50-row pages and rules/export paginate in 500-row batches.

Migration `20261026185020_personal_money_ledger.sql` is additive, applied transactionally through Whatelz Supabase SQL Editor (MCP SQL permission unavailable). No seed money/user records. Undo deployment by reverting the feature; retain the private tables/history rather than deleting financial data.

Design: Taste achromatic-ledger seed 2061286563, existing brand/type and shared shell preserved. Signature is the six-jar allocation ledger, not decorative KPI cards. Question: what have I spent, and what regular bills need recording? Primary action opens a lazy-loaded native dialog; existing data remains during refresh, missing data is distinct from zero. Two-column desktop jars/bills stack on phone. Theme and larger-text layouts retained.

Verification: `node --import tsx --test scripts/personal-money.test.ts scripts/owner-admin.test.ts scripts/auth-routing.test.ts`. Tests execute the actual migration in isolated PGlite for exact totals, currency transfers, void behavior, private grants, atomic recurrence and duplicate prevention; actual API modules are exercised for owner/host/origin and payload boundaries. Browser QA must confirm save/reload, monthly figures, recurring payment/advance, void/restore and phone layout. Only synthetic QA data may be used and must stay clearly identifiable and voided/paused afterward.

Income capture (SPR-186): the form offers Working income, Investment income and Business income, saved in the existing category field. Notes are optional; blank notes use the chosen type as the ledger description. Income enters UNALLOCATED internally; the user chooses only a receiving account, not a jar or expense-purpose/category. Later transfers allocate jars. Existing records are not reclassified, business receipts are not treated as net passive income, and no tax/jar split is automatic.

Date corrections (SPR-188): active Activity entries offer a lazy Edit date dialog. The same owner/origin-gated API accepts only ID, expected original date and new valid date; conditional update also requires not voided. A stale or voided entry fails rather than overwriting it. Only occurred_on changes; recurring_due/next_due and all amounts/accounts stay intact. Activity follows the corrected month, and existing summary/export queries use the new date. Other corrections still use void/replacement. No migration.

Visual-first UI (SPR-189): pastel jar-spending tiles share stable semantic icons; tap to inspect plan/account. Progress compares SGD spending with SGD plan only; other currencies show separate amounts. Activity/Recurring lead with icon, name and amount; row details retain metadata and actions. UI sends include_voided=0 by default; the service filters before count/range. Show voided includes recoverable history, with exact matching pagination. Existing API default include_voided=1 and CSV's complete monthly audit export remain unchanged. Paused rules remain available via Show paused. No record removal. Visual status never replaces accessible names or currency labels.
