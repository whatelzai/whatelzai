# fcOS release notes

Assigned members see a native “What’s new” modal on Home when the latest published release is newer than their own acknowledgement. The latest three entries scroll vertically between a fixed close control and View all footer. Native dialog focus trapping/Escape and a focusable scroll region support keyboard use; no automatic carousel motion. Closing is immediate; acknowledgement persists independently. A failed acknowledgement can show it again next visit. View all closes/acknowledges and opens Profile → Release notes; opening the archive directly does not mark anything seen.

The optional modal streams under its own Home Suspense boundary. Failed news reads stay silent on Home; the Profile archive has a retry state. Archive loads 20 entries with stable publication-time/ID pagination and skips unrelated Profile credit/membership queries. Existing Profile and Usage views are unchanged.

Content is stored in `member_release_notes` (title, newline-separated highlights, publication timestamp, draft/published flag). It is not bundled in application code. Only published entries with publication time at or before now reach assigned members. The archive and modal share the same source and plain-text renderer; no HTML execution. New releases are published through trusted server-side operations; there is no member editing or AI generation.

`member_release_receipts` stores one account-owned latest acknowledgement with its publication timestamp. The server derives users.id through requireAssignedUser; the client supplies only a validated release ID. A service-only SECURITY INVOKER RPC verifies the release is actually published and advances receipts monotonically by publication timestamp/ID, protecting against stale-tab writes and earlier-created scheduled releases. Published timestamps use database-enforced millisecond precision to match JavaScript cursor/receipt ordering. Close invalidates Home routing payloads so navigation back does not resurrect an already-seen popup. No private localStorage or service-worker cache is introduced.

Both tables have RLS and deny all direct anon/authenticated grants; service-role access stays server-side. There are no grants or changes to chats, leads, account links, AI allowances or other member content. Migrations contain schema only. Initial release summaries are inserted into Supabase after checking published deployment history. Publish future updates with a unique slug and truthful member-facing wording; update the publication timestamp only for a new announcement, not a silent typo correction. Database IDs are safe integers for the pilot.

Validation includes publication-order/cursor tampering, assigned-identity gates and account-derived writes, SQL role denial/draft/future denial/monotonic receipts, production build/typecheck/focused lint and browser popup scroll/close/archive/revisit checks. Test-only receipt mutations must target only the explicitly selected QA account and preserve other accounts. The provider advisor MCP is unavailable for this project; explicit grants/RLS and local SQL role tests are the available security checks.
